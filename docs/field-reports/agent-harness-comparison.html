Agent harness comparison

Same greenfield GrokForge Todo prompt across three hosts — how each app feels, what the harness optimizes for, and how we want users to work inside GrokForge.

Field reports: May 2026 · Codex · Cursor · GrokForge

Three hosts at a glance

Velocity harness

OpenAI Codex

Inline plan in chat → Build it → one work stream. Full access writes feel auto-applied. File cards, undo, preview.

Feels like: a fast coworker shipping code.

Balanced harness

Cursor Composer

Plan asks scope questions → .plan.md in repo → Build → Agent for follow-ups. Keep / Undo batches.

Feels like: a PM who clarifies, then an engineer who implements.

Trust + velocity choice

GrokForge

Plan → structured gf-plan → Approve and run → propose_file_edits → diff → Apply (or auto-apply). Desktop IDE + Grok dual-model routing.

Feels like: an intern with power tools — nothing hits disk until you say so (Trust).

What every harness shares

Model + harness Intelligence from the LLM; behavior from prompts, tools, gates, and UI.
Plan → implement Greenfield work starts with an explicit plan beat before bulk edits.
Tool loop Read/search/list (and often edit tools) with user-visible progress.
File-grounded output HTML/CSS/JS (or docs) land as real paths in the workspace.
Iteration Follow-ups (localStorage, delete, styling) without restarting the project.
Undo / review Some form of rollback or diff review exists on every host.

Who does what better (for our use case)

Our use case: dogfood a Grok-native desktop harness — dual-model routing, reviewable writes, evals, voice, multi-root workspaces — not “fastest possible chat widget.”

GrokForge strengths

  • Nothing on disk without validation + user consent (Trust)
  • Monaco diff column for serious review
  • Durable plan.json + approve-and-run handoff
  • Per-model harness profiles (plan vs execute)
  • Edit safety: cascade guard, S&R escalation, truncated-script reject
  • Trust and Velocity temperament in one app
  • Turn traces / eval tags for harness engineering

Borrow from others

  • Codex: rhythm after build; file cards; time-on-task; preview
  • Codex: follow-ups without replanning (→ Work default, 120)
  • Cursor: 1–2 scope questions before plan (persist? delete?)
  • Cursor: PASS-style turn summary (119)
  • Both: verification narrative (tests/browser) — future story

Happy path — GrokForge Todo (how we want you to work)

This is the ideal greenfield run after stories 118 (Work/Plan, Trust/Velocity) and harness fixes (execution model, sample token budget, diff honesty). Adjust temperament in Settings → Agent or the composer chip.

Plan mode Work mode Trust — review before Apply Velocity — auto-apply when valid
1

Open the workspace

File → Open folder · pick empty ToDoApp root

GrokForge creates a stored project (manifest in app data). An empty tree triggers greenfield behavior.

2

Start in Plan

Composer: Plan · model chip: Planning (grok-4.3)

First message on an empty project should default to Plan, not Work. Describe the app in plain language (HTML/CSS/JS, add + complete todos, name “GrokForge Todo”).

3

Let the planner finish

Activity: retrieval · list_directory · “Writing structured plan”

Planner profile uses read-only tools. Final answer includes a gf-plan block. Review the PlanModeCard (steps, files, verification). Expand JSON only if you want the raw artifact.

4

Approve and run

Plan card → Approve and run (Velocity: optional “Build it” label)

Main runs an executor turn with grok-build. Composer moves to Work when execute completes successfully. Do not stay in Plan for follow-ups.

5

Review the proposal

Proposal card · Review diff · editor column

Trust: Open diff, read full content (new files show green preview). Fix scary one-line CSS in the viewer — normalization runs on review. Click Apply all.

Velocity: Valid proposals auto-apply when the turn ends; open diff afterward if you want. Undo uses the last batch snapshot.

6

Verify outside the app

File tree → copy path → open index.html in browser

We do not require an in-app browser. Confirm add/toggle/persist work. If JS fails, ask in Work for a fix — prefer index.html + script.js over a huge inline script.

7

Iterate in Work

Composer: Work · Fast / execution model

“Add localStorage”, “add delete button”, “dark mode” — short messages, executor tools, one composed proposal when possible. Switch to Plan only when you want a new structured plan.

8

When things go wrong

Red tool rows · “Edit proposal failed” · plan card Failed / needs review

If execute produced no files, the plan card should say failed — not Done. Truncated HTML/JS is rejected before Apply. For crushed scripts, use one full-file propose_file_edits after read_file, not endless search_replace.

Trust vs Velocity in one line

TrustYou open every diff and click Apply. Plan mode stays until you switch (greenfield still starts Plan).
VelocityAfter gf-plan, auto Work; valid proposals land on disk without opening diff; undo + review on demand — Codex-like rhythm, GrokForge gates.

Anti-patterns (learned from dogfood)

  • Leaving Plan selected for “add a button” → full replan. Use Work.
  • Assuming Done on the plan stepper means all steps shipped — one execute turn may only bootstrap step 1.
  • Applying a proposal without browser check — truncated <script> can pass closed HTML tags.
  • Using search_replace on a one-line crushed file — use full-file propose_file_edits from rawContent.
